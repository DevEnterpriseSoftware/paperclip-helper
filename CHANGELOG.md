# Changelog

## 1.12.0

- **Watchdog: usage limits pause Codex agents too, not only Claude's.** The usage-limit pause (watchdog 16) now has a recogniser per adapter, which decides from a failed run whether it is an account limit (pause the account's agents until the reset) or transient capacity (left to Paperclip's retries), when the limit resets, and which agents share the account. **Codex** (`codex_local`): the ChatGPT plan's limit ("You’ve hit your usage limit. … Try again at 3:45 PM.", the same wording for the 5-hour and the weekly limit) and the API's quota and billing errors (`insufficient_quota`, "Quota exceeded. Check your plan and billing details.", spend limits, a workspace out of credits or at its spend cap) are limits; "Selected model is at capacity" and "high demand" are transient, whatever error code Paperclip gave them (its CLI path files capacity as `provider_quota`). The wording is the Codex CLI's own (`codex-rs/protocol/src/error.rs`), and each message has a fixture test. Agents on the same `OPENAI_API_KEY` secret share an account, else those on the same Codex login (`CODEX_HOME`), else those on the machine's shared Codex login; a key or home Paperclip redacts makes the agent its own group. One model's own limit ("You’ve hit your usage limit for <model>. Switch to another model now…") pauses only the agent that hit it. Codex writes its reset time in its machine's local time without naming the zone: `WATCHDOG_LIMIT_TIME_ZONE` says which. The installers set it to the time zone of the machine they run on (`TZ`, `timedatectl`, `/etc/timezone` or `/etc/localtime`; on Windows its own zone, converted to its IANA name); a value already in `.env` is kept. Empty, it is the helper's own, which is UTC in its container. A time without a date that has already passed in that zone can only be a mismatch, so it counts as no reset rather than the same time tomorrow. Quota and billing errors give no reset, so the pause is an hour, then 2, 4 and at most 8 while they persist. **Claude** works as before. An adapter without a recogniser is left alone. The board's note names the adapter and the limit ("Codex usage limit reached: …", "Codex quota or billing limit reached: …") and the agents on other adapters that keep working. [docs/watchdog.md](docs/watchdog.md#16-usage-limits)
- **`WATCHDOG_USAGE_LIMIT_PAUSE` replaces `WATCHDOG_LIMIT_PAUSE`.** The old name is still read when the new one isn't set; the installers carry your answer over to the new name and drop the old one from `.env`. Their question now asks about "agents on a plan that hits its usage limit".
- **Watchdog: a review blocked while its participant was paused is restored when that agent is resumed.** When a review stage waits on a paused agent, Paperclip's review recovery blocks the issue with "Paperclip cannot continue the pending execution-review participant because the participant is not invokable…" (cause `execution_review_participant_recovery`), and `executionState.currentParticipant` stays the paused agent. The resume sweep (15) now restores those too: back to `in_review`, which re-pends the stage with its participant and wakes it, with one comment, the same settle window, pacing (the participant's runs) and never-touch rules. The notice is matched on its Recovery details and recovery action where Paperclip shows them, and on its text: its sibling "Paperclip retried the pending execution-review participant once…" (a reviewer that ran and failed) is never touched. The issue may still be assigned to another agent; the parked-issue check (6) doesn't nudge that assignee while the participant is paused or being swept. [docs/watchdog.md](docs/watchdog.md#15-issues-blocked-while-their-agent-was-paused)
- **Watchdog: an agent already paused when the helper starts counts as paused.** Without Paperclip's `pausedAt` (not every release has it), such an agent's pause was taken to start at the helper's first tick, so the issues Paperclip blocked during the pause, before the restart, were never restored on its resume. Now the pause counts from the agent's latest `agent.paused` entry in Paperclip's activity log, or, with none, from an unknown time (any notice that says the agent couldn't be invoked counts, under the usual rules). An agent paused before a restart and resumed before the helper's first look at it is swept too: the activity log shows the resume (within the last day, and never one a sweep already covered).
- **`pch why` knows the newer fixes.** Its recommendations now cover: an agent the watchdog paused at a usage limit (until when, and that it is resumed by itself); a last run that hit its plan's usage limit (Claude or Codex, with the reset time), or only met a busy model, which Paperclip retries; a review blocked because its participant couldn't be woken (resume it, or set the issue back to In review); a review Paperclip escalated to you after its review-round limit; an issue in review with no review stage pending, and who removed its stages; and an agent whose last run finished waiting on a CI run. A cancelled blocker was taken for a dropped wake ("every blocker is done … comment to restart it"), which a comment can't fix: it now says Paperclip never counts a cancelled blocker as resolved, and what to do. For a paused assignee it says whether the resume sweep restores its issues. [docs/commands.md](docs/commands.md#why-what-is-holding-an-issue-and-what-to-do)
- **Installers: easier to read.** Colour on a terminal (red section headings, bold questions, the value Enter keeps in cyan, a green tick for what worked, yellow warnings; `NO_COLOR` turns it off), a blank line after each answer, and a line on what goes wrong before each watchdog question, so each says what it fixes. With the usage-limit pause on, the installer writes the machine's time zone as `WATCHDOG_LIMIT_TIME_ZONE` (for Codex's reset times), unless your settings have one.
- **`pch help` and `pch status` are easier to read.** Help groups the commands (what's going on, decide and unblock, housekeeping, costs, setup) and fits 100 columns; usage errors all read `usage: pch …`. Status gives each component one line and its counts below it, says plainly when the service isn't running, and names the start time in UTC rather than a raw timestamp. An expired key says so instead of "in -3 days".
- **Relay: a Paperclip outage no longer loses a merge decision.** Looking up the PR's issues treated every failed request as "no such issue", so with Paperclip down (or the key revoked) a merge was answered "no Paperclip issue found", the delivery was recorded, and GitHub's Redeliver got "duplicate". Only a 404 or 403 means not found now; anything else fails the delivery (502), which is forgotten so Redeliver works. A merge-queue job that fails is forgotten on disk too, not only in memory.
- **Relay: a merge note that isn't a decision says so.** When your merge's issue wasn't waiting on you, its comment began "Approved: PR #8 merged…" though nothing was approved. It now reads "PR #8 merged…" with "_Not recorded as a decision: …_" and why. An organisation webhook's ping is answered (it names no repository); a `/approve` in a review is called that in the PR note, not `/changes`; notes posted on GitHub are signed as the helper's, not "Relayed from GitHub".
- **Watchdog: a dry run records nothing.** It recorded the one automatic release of a hold Paperclip can't release (so with dry run off, the release never came, and the log called it "back") and spent the retries of deferred wakes. Both are now logged once and recorded only when they happen. A release Paperclip refuses is reported once and left to you, never called "back".
- **Watchdog: one failing check no longer stops the rest.** A listing Paperclip refused, say, aborted the whole tick, for that company and every one after it. Each check now runs on its own: the others carry on, the log names the check that failed, and `pch status` shows it. A failure to read the key's identity is recorded too.
- **Records of something still going on aren't forgotten.** The state file keeps 2,000 watchdog records and dropped the oldest beyond that, including a card's routed issue (so the card would be routed again), an agent's pause (so its resume was missed) and a usage-limit pause (so its agents weren't resumed). Those are now kept; only counts of what was done are dropped. A resume sweep that ends early (the agent paused again, or terminated) no longer leaves check 6 ignoring its issues until the next restart.
- **Relay: your own lines in the Pull requests document are kept.** Past 200 entries the relay trimmed every bullet line, a person's too; it now trims only its own.
- **Cost sync: a malformed prices file is reported, not renamed aside.** A syntax error in `data/prices.json` moved it to `prices.json.corrupt-…` without a word and the built-in prices were used; now the log says so and the file stays for you to fix. The file is read again only when it changes.
- **Cost sync: a lost state file is recovered from the activity log.** With no state file, the runs your earlier cost posts name are counted as synced, so only the rest are posted; when the log's 500-entry window is full, nothing older than its oldest entry is synced; when the posts don't name their runs, or the log can't be read, only runs that finish from now on. This used to be skipped whenever `COST_SYNC_SINCE` was set, which the installer does, so on a Paperclip that ignores idempotency keys a lost `data/` could post every run again.
- **Cost sync: one stuck post no longer stalls everything.** A post with an unknown outcome being retried, or one company's failing scan, stopped the whole pass for up to 75 minutes; now only a refusal of the key itself (401, 403, 429) stops it, and other runs and companies carry on. A post is resent without its issue only when Paperclip says the issue is gone (404, 422), not on a 429.
- **GitHub reads are retried once** after a dropped connection, a 5xx or a short secondary rate limit; writes never are. A secondary rate limit is reported as a rate limit, not a missing permission, and the permission hint names Checks or Contents where those are what's missing.
- **`pch usage` counts interrupted runs,** as failures. `RELAY_PORT` outside 0–65535 is reported.
- **Cost sync: Codex runs were priced too low since Paperclip 2026.10.** Paperclip now stores Codex's input net of cache reads (`rawInputIncludesCached: false`; before, it stored Codex's own input, which includes them). Cost sync subtracted the cache reads a second time, so a well-cached run's fresh input was priced at nothing: 100K fresh input, 900K cache reads and 50K output on gpt-6.1-sol came to $0.51 instead of $0.79. Runs with the mark are now taken as they are; runs without it as before. ACP-engine cache writes (from the run's breakdown) are priced at the write price. `pch usage` showed Codex fresh input too low for the same reason, and is fixed the same way.
- **Cost sync: Claude runs are no longer posted well below what their tokens cost.** Claude Code reports its own cost, and cost sync posted it as is. Two cases came out low: a run that stopped before Claude reported a cost (killed, timed out) was never posted at all; and with the ACP engine (Paperclip's default for Claude), a run's cost is the growth of its session's running cost, which understates the run when the agent process restarted and its running cost restarted with it. Cost sync now prices each Claude run's tokens at Anthropic's list price (new Anthropic entries in the price table, checked 2026-10-24): model by model when Paperclip split the run by model (`usageByModel`), and not at all for a `mixed` run without the split. A reported cost more than 10% below that is raised to it; a run with no reported cost gets it. Such events are posted with `costStatus: "estimated"`. The run is only fetched when its tokens could cost clearly more than reported. A run with no recorded model is priced with the agent's configured model (Codex too, before `CODEX_DEFAULT_MODEL`). On the ACP engine, a Codex run's requested fast mode is doubled only on models that have fast mode, as Paperclip applies it.
- **Cost sync: each event carries an idempotency key** (`pch-cost-sync:<run id>`). Paperclip 2026.10 and later record a key once. While the latest post shows the key is honoured (checked on every post, so a downgraded or restored Paperclip is noticed), a post whose answer was lost (a timeout, a dropped connection, the helper stopping mid-post) is posted again with the same body and key on the next pass, up to 5 times, instead of being given up; a key Paperclip already holds for other figures counts the run as synced. This also makes a lost state file safe on those versions. On an older Paperclip, nothing changes.
- **Cost sync: a 401, 403 or 429 no longer skips runs for good.** Any rejection used to mark the run as skipped, so a revoked key or rate limiting during a pass lost every run in it. Only 400, 404 and 422 (a problem with the event itself) skip the run now; anything else stops the pass and the runs are posted on a later one.
- **`pch costs --audit [--days N]`: check the figures.** Read-only. For every subscription run of the last N days (default 7), per agent: fresh input, cache reads and writes, output, the cost reported, what the tokens cost at list price, and what cost sync posts; how many Claude runs reported no cost or clearly less than their tokens cost; what was synced, skipped, or is before the sync start; how many runs' details couldn't be read; whether idempotency keys are honoured; and duplicates (runs Paperclip listed twice, runs you posted more than one event for). [docs/cost-sync.md](docs/cost-sync.md#checking-the-figures)
- **Price table checked 2026-10-24** against OpenAI's and Anthropic's published prices; OpenAI cache-write prices added.
- **Code: smaller modules.** The watchdog's CI-run check (11) moved into `ci-runs.mjs` and its checks for issues waiting on your review (12, 13) into `board-held.mjs`, next to their helpers; `pch why` moved out of `commands.mjs` into `why.mjs`. Constants that were copied between modules (active and finished run statuses, closed issue statuses, the PR label, the watchdog's signature, the paused-task refusal) live once in `util.mjs`. The watchdog went from 2,100 to 1,670 lines, `commands.mjs` from 990 to 740.
- **Tests:** 412 in all, among them one for each fix above. The fake Paperclip logs `agent.paused` and `agent.resumed` activity, re-pends a review stage with its participant when an issue goes back to review, and can fail one listing by its query.

## 1.11.0

- **Relay: a merge that is only one step of an issue no longer closes it.** Approve-on-merge recorded your approval on the issue's pending stage, and Paperclip closed it as `done`, releasing its dependants, even when the PR was only part of the issue's work (a fix found halfway through a verification, one slice of several); nothing woke the implementer, and the rest of the work was silently dropped. Paperclip can't approve a stage and hand the work back ([paperclipai/paperclip#10360](https://github.com/paperclipai/paperclip/issues/10360)). Now, before approving, the relay looks for `RELAY_MERGE_KEEP_OPEN_MARKER` (default `Merge does not complete this issue`, any case) in the issue's description, its review request, and the implementer's hand-off since the issue last moved to review (Paperclip's activity log, the implementer's own move to review; an earlier round's hand-off doesn't count). With the marker, the merge is still relayed, but as your **changes requested**: the issue goes back to its implementer, who is woken with "PR #n merged (`<sha>`). This issue says the merge doesn't complete it, so it's back with you for the rest of the work." With `RELAY_MERGE_KEEP_OPEN_CHILDREN=true` (default `false`), open child issues keep it open the same way. Otherwise nothing changes: approved and closed. The same check applies before the relay closes an issue whose stages were wiped. If Paperclip refuses the hand-back, the relay comments and leaves the issue as it was. A marker in the description hands back every merge, the last one too: finish such an issue with `/approve`. An empty marker turns the check off. The agents have to write the marker: the README and docs/relay.md give a line for the team's agent template, which must quote the same phrase as the setting. [docs/relay.md](docs/relay.md#keeping-an-issue-open-after-a-merge)
- **README: approving the last stage always closes the issue** is listed among the Paperclip issues the helper works around (#10360; fix proposed in #10365).

## 1.10.0

- **Watchdog: issues blocked while their agent was paused are restored when it is resumed.** Pausing an agent with runs queued or in flight makes Paperclip's recovery give up on each affected issue: it is set to `blocked` with a system comment ("the original assignee is not invokable", Recovery owner: Board decision required), and resuming the agent restarts none of them; each needed setting back by hand. With `WATCHDOG_RESUME_SWEEP` (default `true`) the watchdog remembers every agent's status each tick, in the state file. When an agent goes from paused to available and stays so for `WATCHDOG_RESUME_SETTLE_MIN` minutes (default 10; a pause within that window restores and wakes nothing), it restores each of its blocked issues whose newest comment is that recovery notice, posted while the agent was paused (after Paperclip's `pausedAt`), with no unresolved blocker (done and cancelled blockers don't count), no status change since, and a recovery action, when Paperclip shows one, of the "assignee not invokable" kind. The notice is recognised by its **Recovery** section; on a Paperclip without comment details, by its text. Each issue goes back to `in_review` if a review stage is pending (so the stage's participant is woken, and the stage isn't dissolved), else to the status Paperclip recorded before the block, else `todo`, with one comment; that wakes the assignee. Never more than `WATCHDOG_RESUME_SWEEP_LIMIT` runs in flight for the agent (default `0`: its `maxConcurrentRuns`, or 1 if Paperclip doesn't show one), counting every run it has queued or going on any issue, including the wakes Paperclip releases on the resume, most urgent first; the rest follow on later ticks. The agent is read again just before each restore. The parked-issue check (6) waits for the settle window too, and its nudges share the same per-agent limit. A block from while the agent was running, an issue anyone has commented on or moved since, and an issue blocked for any other reason are never touched; when the recovery action can't be read, it waits rather than guess. While a sweep is under way, the parked-issue check (6) leaves alone the issues it is still to restore. The installers ask about it. [docs/watchdog.md](docs/watchdog.md#15-issues-blocked-while-their-agent-was-paused)
- **Watchdog: Claude usage limits pause the agents until the reset.** When a Claude subscription hits its 5-hour or weekly limit (or an API organisation its spend limit), every Claude agent's next run fails and Paperclip keeps retrying them: hundreds of failed runs a night. With `WATCHDOG_LIMIT_PAUSE` (default `true`), a `claude_local` run that failed with the limit wording (`claude_transient_upstream` or `provider_quota`; a plain transient failure such as "exited with code 143" doesn't count) pauses every Claude agent on the same account (the same `ANTHROPIC_API_KEY` secret, else the same `CLAUDE_CODE_OAUTH_TOKEN` secret, whatever each agent's `CLAUDE_CONFIG_DIR`; with neither, the login stored on the machine), each only once it has no run queued or going, read again just before the pause, so no run is cut off; an agent kept busy for 30 ticks is logged. The reset time and zone come from the message; with none (or one more than a week away) it tries again after an hour, backing off to 8 hours while the limit persists. The board is told once per limit, in the log and on `WATCHDOG_NOTIFY_ISSUE` if that issue is in the same company. `WATCHDOG_LIMIT_RESUME_GRACE_MIN` (default 5) minutes after the reset, exactly the agents the watchdog paused are resumed (never one you paused; a refused resume is retried), and the resume sweep restores their issues. Agents whose account can't be compared (a plain-text token, their own Claude config directory with no token, Bedrock, a proxy, a managed connection) are paused only when they fail themselves. Codex agents' quota failures are left to Paperclip's retries. The installers ask about it. [docs/watchdog.md](docs/watchdog.md#16-usage-limits)
- **Relay: a PR the merge queue drops without a conflict.** A drop for a conflict was sent back; any other drop left the PR sitting unmerged until someone noticed. With `RELAY_MERGE_QUEUE` (default `true`; needs a GitHub token with **Actions: Read**, and without one the log says once that it is off), when `github-merge-queue[bot]` removes a PR, the relay goes by GitHub's reason and the PR's latest merge-group runs: `CI_FAILURE` with a **failed job** (or one that timed out: its own `timeout-minutes`) sends the PR back to its implementer like a conflict, with the run, the failed jobs and the first failure annotation; a **cancelled job** (a runner restarted), `CI_TIMEOUT` (the queue's status-check timeout), or a conflict only with a PR ahead in the queue isn't the PR's fault, so the board is told to queue it again, without waking the implementer (on the issue only while it waits on a person; otherwise on the PR and in the board notes). Other reasons are left alone. `RELAY_REQUEUE_ON_INFRA_DROP` (default `false`) re-queues such a PR itself, once per head commit, only one a person queued; it needs a token allowed to merge. Once per merge group. [docs/relay.md](docs/relay.md#prs-the-merge-queue-drops-without-a-conflict)
- **Watchdog and relay: issues whose review stages were wiped.** An agent's update that sends `executionPolicy.stages: []` removes the issue's reviews (a Paperclip bug, seen with Codex agents): the issue closes as done with its PR open and unreviewed, or sits in review with nothing to review, and its dependants can't start. With `WATCHDOG_STAGES_WIPE` (default `true`), a done issue whose stages an agent removed (Paperclip's activity log shows it) and whose own PR, opened before it was done, is still open (its PR work products and the PR links in the relay's notes and its comments; needs a GitHub token) is set back to `in_progress` with a comment saying its stages must be restored, once (closed again, the board is told instead), and an issue in progress or in review whose stages an agent removed is reported; the board is told either way. Stages are never re-created; an issue that never had stages, or whose stages a person removed, is left alone. With `RELAY_DONE_WITHOUT_STAGES` (default `true`), when you merge such an issue's own PR, the relay closes it as done, as the approval would have, so its dependants are released. [docs/watchdog.md](docs/watchdog.md#17-issues-whose-review-stages-were-wiped)
- **`pch usage [--days N] [--agent NAME]`: where the tokens go.** Read-only. Per agent over the last 7 days: finished runs and failures, input, cached and output tokens, the cost Paperclip records, model and effort; what woke it (each run's wake reason); and flags: an agent that polls (more than 25% of its runs are its own monitor's wakes), one whose runs keep failing, and one using far more than an even share of its provider's tokens. [docs/commands.md](docs/commands.md#usage-where-the-tokens-go)
- **`pch answer ISSUE CARD "text"`: answer a question card from the command line.** As the card's form does: a typed answer as `otherText` (the field Paperclip reads; `text` is ignored, which is why answers sent by hand were refused), or the option whose label matches; a text question always takes a typed answer. Cards with one question. [docs/commands.md](docs/commands.md#the-pch-commands)
- **Relay: notes that need nothing from the agent no longer wake it.** "PR #12 opened by …", "closed without merging" and "merged by someone else" were comments, and every board comment wakes the issue's agent. Paperclip has no comment that doesn't wake; with `RELAY_QUIET_NOTES` (default `true`) they go in the issue's **Pull requests** document instead, one dated line each, which wakes nobody and still links the PRs (anything you add to it is kept). If Paperclip won't take the document, a comment as before. [docs/relay.md](docs/relay.md#quiet-notes)
- **README: the Paperclip issues it works around.** A table of the open Paperclip issues (and proposed fixes) behind each watchdog check and the relay, so you can follow the upstream fix and switch the check off once it ships.
- **README: why it saves tokens.** A short section on what the event-driven wakes replace: monitor wakes that reload an agent's whole context only to find CI still running, with one company's figures as an example. The watchdog guide, the settings table and `.env.example` now say to rely on the Helper or space monitors widely (30 minutes or more), not both at short intervals.
- **Watchdog: a monitor that watches the reported run is cleared.** A Paperclip monitor still due used to keep the CI-run report back, and agents that keep a long monitor on a verification run woke once more after it finished. When the monitor's notes name the run being reported and nothing else, the watchdog now reports it anyway and clears that monitor in the same step (one `PATCH` with the comment and the issue's current execution policy without its monitor). A monitor that also names another run, or names nothing, is left alone and still keeps the report back.
- **`pch status`** counts the issues restored after their agent was resumed, the agents paused and resumed at a usage limit, the done issues reopened because their PR was still open, and the wiped review stages reported.
- **Tests:** the fake Paperclip can wake an issue's assignee on a board status change or comment (`db.simulateWakes`), so a test can see the run the wake queues, and its comments carry `createdAt` and author fields.

## 1.9.0

- **Watchdog: default-branch dispatches always report their verdict.** A `workflow_dispatch` run on the repository's default branch, read from GitHub, is never automatically re-run or silenced after the branch moves on. Every conclusion, including `cancelled`, wakes the waiting agent through the usual CI-run check. Push, pull-request and other-branch dispatch runs keep their existing rules. The default branch is read once an hour per repository; while GitHub won't say, such a run waits for the next scan (never re-run meanwhile) and the log says why once.
- **Watchdog: a CI run named before the agent's latest comment is reported.** An agent often names the run once and follows up without repeating it ("blocked on run …", then "cleared a dependency; still waiting on CI"). Only the latest comment was read, so the run was never found and the agent was never told. When the latest comment names no run, the agent's latest comment that does now counts. A run that finished before the agent last commented still isn't reported.
- **Watchdog: a queued wake that never starts no longer silences the CI report.** A Paperclip monitor's wake can sit queued for hours after the monitor fires, and the watchdog took it as the agent about to run. With nothing running on the issue, a queued wake now holds the report back for the stall window only; after that the run is reported, and the comment's wake joins the queued one. A wake deferred behind an earlier run still holds it back, as before.
- **Watchdog: a monitor holds the CI report back only while it will still act:** scheduled, with its next check ahead or just due. Past its timeout or out of attempts it still counts under the default recovery policy (`wake_owner`, which wakes the agent at that check), and no longer counts under `create_recovery_issue` or `escalate_to_board`. A scheduled monitor whose next check is more than two minutes overdue no longer counts. `triggered` and `cleared` monitors never did.
- **Watchdog: why a finished CI run wasn't reported is logged** at debug level, once per run attempt and reason. A token GitHub refuses to show runs to is warned about once per repository, with the permission it needs, instead of a debug line every scan.

## 1.8.1

- **`pch worktrees`: squash-merged branches are closed.** A squash merge puts new commits on the base branch, so every squash-merged worktree showed "commits not on origin/master" and was left for you: on a real instance, 20 of 23. With `GITHUB_TOKEN` or `GITHUB_TOKEN_FILE` set, the command now asks GitHub for the branch's PR; a merged PR with at least as many commits as the worktree is ahead holds them all, and the worktree is closed ("PR #41 merged"). A worktree with more commits than its PR is still left for you, with both counts.
- **`pch worktrees`: a workspace whose clean-up failed is listed, not closed.** Paperclip counts `cleanup_failed` as closed and answers 404 to closing it again, so `--apply` reported "not closed … 404" for them. They're now listed apart, with their folder and why the clean-up failed, so you can remove a folder that's still there.
- **`pch worktrees`: sessions on the project's shared checkout are counted, not listed.** Closing one frees nothing; they filled the list one line per session.
- **`pch worktrees --apply`** says "already closed" for a workspace Paperclip's reaper closed between the preview and the close.

## 1.8.0

- **`pch worktrees [--apply]`: finished issues' worktrees still on disk.** Paperclip removes a workspace's git worktree when the workspace is closed, but its reaper only closes one once it can prove the branch was delivered, the worktree is clean (untracked build output counts) and the issue has been finished for 7 days. Squash merges and PRs Paperclip can't read keep a worktree for good, so they piled up: hundreds of worktrees, tens of GB. The command lists the open workspaces of issues finished at least a day ago (`--min-days=N`), with what Paperclip's own close check says about each, and `--apply` closes the ones that are safe, as their Close button does: Paperclip removes the worktree and records it. Workspaces with modified files are always left for you; with untracked files or commits not on the base branch unless you pass `--include-untracked` or `--include-unmerged`. A workspace whose clean-up failed before is retried, and a failed clean-up's output is printed. [docs/commands.md](docs/commands.md#worktrees-finished-issues-worktrees-still-on-disk)
- **Watchdog: agents hear when the CI run they wait on has finished.** An agent that pushes says it waits on a run ("waiting on run 39498202022", or a link) and stops, or schedules a monitor that gives up before the run is done; a run queued behind others can finish hours later, and nothing woke the agent. With `WATCHDOG_CI_RUNS` (default `true`) and a GitHub token with **Actions: Read**, the watchdog reads the run named in the agent's latest comment or its monitor's notes, and once the run has finished and the agent hasn't run on the issue since, comments with the result and the failed jobs. Once per run attempt, about the newest run named; a monitor that will still fire is left to do it, and a cancelled run, or one whose branch has moved on, isn't reported. [docs/watchdog.md](docs/watchdog.md#11-ci-runs-an-agent-waits-on)
- **Watchdog: known flaky CI jobs are re-run.** With `WATCHDOG_CI_RERUN_JOBS` set to a pattern of job names, a run the agent waits on whose failed jobs all match is re-run (GitHub's "Re-run failed jobs") before it is reported, up to `WATCHDOG_CI_RERUN_MAX` (2) times, and only while it is still its PR's head. Needs **Actions: Read and write**. Off unless set.
- **Watchdog: answers that reach nobody are delivered.** While a review waits on you, Paperclip assigns the issue to you, so when you answer the agent's card then, the answer wakes you, not the agent. With `WATCHDOG_DELIVER_ANSWERS` (default `true`) the watchdog returns such an issue to the agent that asked, as your "changes requested", with your answer quoted, at least 30 minutes after you answered, when no run of the agent saw the answer and the card asked for a wake. Never on a review Paperclip escalated to you. Once per card. [docs/watchdog.md](docs/watchdog.md#12-answers-that-reach-nobody)
- **Watchdog: reviews escalated by Paperclip's review-round limit can go back to the implementer.** After three agent change requests in a row on one review stage (`maxReviewRounds`), Paperclip hands the review to the responsible person instead of back to the implementer. That is deliberate, so it stays with you by default; with `WATCHDOG_RETURN_ESCALATED_REVIEWS=true` the watchdog returns it to the implementer with the reviewer's latest request, `WATCHDOG_MAX_NUDGES` times per issue (each return, as your decision, gives the agents `maxReviewRounds` more rounds). Raising `maxReviewRounds` in your execution policies is the other way. [docs/watchdog.md](docs/watchdog.md#13-reviews-escalated-by-paperclips-review-round-limit)
- **Watchdog: issues blocked by a cancelled issue.** Paperclip never counts a cancelled blocker as resolved, so its dependents stay blocked and nothing wakes their agents. With `WATCHDOG_CANCELLED_BLOCKERS` (default `true`) the watchdog tells the dependent's agent once, quoting the blocker's last comment, so it can remove or replace the blocker. [docs/watchdog.md](docs/watchdog.md#14-issues-blocked-by-a-cancelled-issue)
- **Relay: a PR's link goes on its own issue.** A newly opened PR's URL was posted on whichever issue waited on you among those the PR names, their subtasks and their blockers, so a PR could show up as another issue's (one PR was linked on the issue blocking its own). It now goes on the first issue the PR names, or that issue's subtask waiting on you. Your merge decisions still look further.
- **Watchdog: a dry run no longer uses up nudges.** With `DRY_RUN=true` the watchdog recorded each nudge it would have sent, so once dry run was off those situations counted as handled. It now logs each once and records nothing.
- **`pch status`** counts finished CI runs reported, flaky runs re-run and issues returned to their agent. The installers ask about the new settings.
