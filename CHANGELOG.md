# Changelog

## 1.10.0

- **Watchdog: issues blocked while their agent was paused are restored when it is resumed.** Pausing an agent with runs queued or in flight makes Paperclip's recovery give up on each affected issue: it is set to `blocked` with a system comment ("the original assignee is not invokable", Recovery owner: Board decision required), and resuming the agent restarts none of them; each needed setting back by hand. With `WATCHDOG_RESUME_SWEEP` (default `true`) the watchdog remembers every agent's status each tick, in the state file. When an agent goes from paused to available, it restores each of its blocked issues whose newest comment is that recovery notice, posted while the agent was paused (after Paperclip's `pausedAt`), with no unresolved blocker (done and cancelled blockers don't count), no status change since, and a recovery action, when Paperclip shows one, of the "assignee not invokable" kind. The notice is recognised by its **Recovery** section; on a Paperclip without comment details, by its text. Each issue goes back to `in_review` if a review stage is pending (so the stage's participant is woken, and the stage isn't dissolved), else to the status Paperclip recorded before the block, else `todo`, with one comment; that wakes the assignee. At most `WATCHDOG_RESUME_SWEEP_LIMIT` issues per agent per tick (default `0`: the agent's `maxConcurrentRuns`, or 1 if Paperclip doesn't show one), counting those restored earlier whose runs are still queued or going, most urgent first; the rest follow on later ticks. A block from while the agent was running, an issue anyone has commented on or moved since, and an issue blocked for any other reason are never touched; when the recovery action can't be read, it waits rather than guess. While a sweep is under way, the parked-issue check (6) leaves alone the issues it is still to restore. The installers ask about it. [docs/watchdog.md](docs/watchdog.md#15-issues-blocked-while-their-agent-was-paused)
- **Watchdog: Claude usage limits pause the agents until the reset.** When a Claude subscription hits its 5-hour or weekly limit (or an API organisation its spend limit), every Claude agent's next run fails and Paperclip keeps retrying them: hundreds of failed runs a night. With `WATCHDOG_LIMIT_PAUSE` (default `true`), a `claude_local` run that failed with the limit wording (`claude_transient_upstream` or `provider_quota`; a plain transient failure such as "exited with code 143" doesn't count) pauses every Claude agent on the same account (the same `CLAUDE_CODE_OAUTH_TOKEN` secret, or the machine's own login), each only once it has no run queued or going, so no run is cut off. The reset time and zone come from the message; with none (or one more than a week away) it tries again after an hour, backing off to 8 hours while the limit persists. The board is told once per limit, in the log and on `WATCHDOG_NOTIFY_ISSUE` if that issue is in the same company. `WATCHDOG_LIMIT_RESUME_GRACE_MIN` (default 5) minutes after the reset, exactly the agents the watchdog paused are resumed (never one you paused; a refused resume is retried), and the resume sweep restores their issues. Agents whose account can't be compared (a plain-text token, Bedrock, their own Claude config, a proxy, a managed connection) are paused only when they fail themselves. Codex agents' quota failures are left to Paperclip's retries. The installers ask about it. [docs/watchdog.md](docs/watchdog.md#16-claude-usage-limits)
- **Relay: a PR the merge queue drops without a conflict.** A drop for a conflict was sent back; any other drop left the PR sitting unmerged until someone noticed. With `RELAY_MERGE_QUEUE` (following `RELAY_FIX_CONFLICTS` unless set; needs a GitHub token with **Actions: Read**), when `github-merge-queue[bot]` removes a PR, the relay goes by GitHub's reason and the PR's latest merge-group runs: `CI_FAILURE` with a **failed job** sends the PR back to its implementer like a conflict, with the run, the failed jobs and the first failure annotation; a **cancelled job** (a runner restarted), `CI_TIMEOUT` (the queue's status-check timeout), or a conflict only with a PR ahead in the queue isn't the PR's fault, so the board is told to queue it again, without waking the implementer (on the issue only while it waits on a person; otherwise on the PR and in the board notes). Other reasons are left alone. `RELAY_REQUEUE_ON_INFRA_DROP` (default `false`) re-queues such a PR itself, once per head commit, only one a person queued; it needs a token allowed to merge. Once per merge group. [docs/relay.md](docs/relay.md#prs-the-merge-queue-drops-without-a-conflict)
- **Watchdog and relay: issues whose review stages were wiped.** An agent's update that sends `executionPolicy.stages: []` removes the issue's reviews (a Paperclip bug, seen with Codex agents): the issue closes as done with its PR open and unreviewed, or sits in review with nothing to review, and its dependants can't start. With `WATCHDOG_STAGES_WIPE` (default `true`), a done issue whose stages an agent removed (Paperclip's activity log shows it) and whose own PR, opened before it was done, is still open (its PR work products and the PR links in the relay's notes and its comments; needs a GitHub token) is set back to `in_progress` with a comment saying its stages must be restored, once (closed again, the board is told instead), and an issue in progress or in review whose stages an agent removed is reported; the board is told either way. Stages are never re-created; an issue that never had stages, or whose stages a person removed, is left alone. With `RELAY_DONE_WITHOUT_STAGES` (default `true`), when you merge such an issue's own PR, the relay closes it as done, as the approval would have, so its dependants are released. [docs/watchdog.md](docs/watchdog.md#17-issues-whose-review-stages-were-wiped)
- **`pch usage [--days N] [--agent NAME]`: where the tokens go.** Read-only. Per agent over the last 7 days: finished runs and failures, input, cached and output tokens, the cost Paperclip records, model and effort; what woke it (each run's wake reason); and flags: an agent that polls (more than 25% of its runs are its own monitor's wakes), one whose runs keep failing, and one using far more than an even share of its provider's tokens. [docs/commands.md](docs/commands.md#usage-where-the-tokens-go)
- **`pch answer ISSUE CARD "text"`: answer a question card from the command line.** As the card's form does: a typed answer as `otherText` (the field Paperclip reads; `text` is ignored, which is why answers sent by hand were refused), or the option whose label matches. Cards with one question. [docs/commands.md](docs/commands.md#the-pch-commands)
- **Relay: notes that need nothing from the agent no longer wake it.** "PR #12 opened by …", "closed without merging" and "merged by someone else" were comments, and every board comment wakes the issue's agent. Paperclip has no comment that doesn't wake; with `RELAY_QUIET_NOTES` (default `true`) they go in the issue's **Pull requests** document instead, one dated line each, which wakes nobody and still links the PRs (anything you add to it is kept). If Paperclip won't take the document, a comment as before. [docs/relay.md](docs/relay.md#quiet-notes)
- **README: why it saves tokens.** A short section on what the event-driven wakes replace: monitor wakes that reload an agent's whole context only to find CI still running, with one company's figures as an example. The watchdog guide, the settings table and `.env.example` now say to rely on the Helper or space monitors widely (30 minutes or more), not both at short intervals.
- **Watchdog: a monitor that watches the reported run is cleared.** A Paperclip monitor still due used to keep the CI-run report back, and agents that keep a long monitor on a verification run woke once more after it finished. When the monitor's notes name the run being reported and nothing else, the watchdog now reports it anyway and clears that monitor in the same step (one `PATCH` with the comment and the issue's current execution policy without its monitor). A monitor that also names another run, or names nothing, is left alone and still keeps the report back.
- **`pch status`** counts the issues restored after their agent was resumed, the agents paused and resumed at a usage limit, the done issues reopened because their PR was still open, and the wiped review stages reported.
- **Tests:** the fake Paperclip can wake an issue's assignee on a board status change or comment (`db.simulateWakes`), so a test can see the run the wake queues, and its comments carry `createdAt` and author fields.

## 1.9.0

- **Watchdog: default-branch dispatches always report their verdict.** A `workflow_dispatch` run on the repository's default branch, read from GitHub, is never automatically re-run or silenced after the branch moves on. Every conclusion, including `cancelled`, wakes the waiting agent through the usual CI-run check. Push, pull-request and other-branch dispatch runs keep their existing rules. The default branch is read once an hour per repository; while GitHub won't say, such a run waits for the next scan (never re-run meanwhile) and the log says why once.
- **Watchdog: a CI run named before the agent's latest comment is reported.** An agent often names the run once and follows up without repeating it ("blocked on run …", then "cleared a dependency; still waiting on CI"). Only the latest comment was read, so the run was never found and the agent was never told. When the latest comment names no run, the agent's latest comment that does now counts. A run that finished before the agent last commented still isn't reported.
- **Watchdog: a queued wake that never starts no longer silences the CI report.** A Paperclip monitor's wake can sit queued for hours after the monitor fires, and the watchdog took it as the agent about to run. With nothing running on the issue, a queued wake now holds the report back for the stall window only; after that the run is reported, and the comment's wake joins the queued one. A wake deferred behind an earlier run still holds it back, as before.
- **Watchdog: a monitor holds the CI report back only while it will still act:** scheduled, with its next check ahead or just due. Past its timeout or out of attempts it still counts under the default recovery policy (`wake_owner`, which wakes the agent at that check), and no longer counts under `create_recovery_issue` or `escalate_to_board`. A scheduled monitor whose next check is more than two minutes overdue no longer counts. `triggered` and `cleared` monitors never did.
- **Watchdog: why a finished CI run wasn't reported is logged** at debug level, once per run attempt and reason. A token GitHub refuses to show runs to is warned about once per repository, with the permission it needs, instead of a debug line every scan.

## 1.8.1

- **`pch worktrees`: squash-merged branches are closed.** A squash merge puts new commits on the base branch, so every squash-merged worktree showed "commits not on origin/master" and was left for you: on a real instance, 20 of 23. With `GITHUB_TOKEN` or `GITHUB_TOKEN_FILE` set, the command now asks GitHub for the branch's PR; a merged PR with at least as many commits as the worktree is ahead holds them all, and the worktree is closed ("PR #41 merged"). A worktree with more commits than its PR is still left for you, with both counts.
- **`pch worktrees`: a workspace whose clean-up failed is listed, not closed.** Paperclip counts `cleanup_failed` as closed and answers 404 to closing it again, so `--apply` reported "not closed … 404" for them. They're now listed apart, with their folder and why the clean-up failed, so you can remove a folder that's still there.
- **`pch worktrees`: sessions on the project's shared checkout are counted, not listed.** Closing one frees nothing; they filled the list one line per session.
- **`pch worktrees --apply`** says "already closed" for a workspace Paperclip's reaper closed between the preview and the close.

## 1.8.0

- **`pch worktrees [--apply]`: finished issues' worktrees still on disk.** Paperclip removes a workspace's git worktree when the workspace is closed, but its reaper only closes one once it can prove the branch was delivered, the worktree is clean (untracked build output counts) and the issue has been finished for 7 days. Squash merges and PRs Paperclip can't read keep a worktree for good, so they piled up: hundreds of worktrees, tens of GB. The command lists the open workspaces of issues finished at least a day ago (`--min-days=N`), with what Paperclip's own close check says about each, and `--apply` closes the ones that are safe, as their Close button does: Paperclip removes the worktree and records it. Workspaces with modified files are always left for you; with untracked files or commits not on the base branch unless you pass `--include-untracked` or `--include-unmerged`. A workspace whose clean-up failed before is retried, and a failed clean-up's output is printed. [docs/commands.md](docs/commands.md#worktrees-finished-issues-worktrees-still-on-disk)
- **Watchdog: agents hear when the CI run they wait on has finished.** An agent that pushes says it waits on a run ("waiting on run 39498202022", or a link) and stops, or schedules a monitor that gives up before the run is done; a run queued behind others can finish hours later, and nothing woke the agent. With `WATCHDOG_CI_RUNS` (default `true`) and a GitHub token with **Actions: Read**, the watchdog reads the run named in the agent's latest comment or its monitor's notes, and once the run has finished and the agent hasn't run on the issue since, comments with the result and the failed jobs. Once per run attempt, about the newest run named; a monitor that will still fire is left to do it, and a cancelled run, or one whose branch has moved on, isn't reported. [docs/watchdog.md](docs/watchdog.md#11-ci-runs-an-agent-waits-on)
- **Watchdog: known flaky CI jobs are re-run.** With `WATCHDOG_CI_RERUN_JOBS` set to a pattern of job names, a run the agent waits on whose failed jobs all match is re-run (GitHub's "Re-run failed jobs") before it is reported, up to `WATCHDOG_CI_RERUN_MAX` (2) times, and only while it is still its PR's head. Needs **Actions: Read and write**. Off unless set.
- **Watchdog: answers that reach nobody are delivered.** While a review waits on you, Paperclip assigns the issue to you, so when you answer the agent's card then, the answer wakes you, not the agent. With `WATCHDOG_DELIVER_ANSWERS` (default `true`) the watchdog returns such an issue to the agent that asked, as your "changes requested", with your answer quoted, at least 30 minutes after you answered, when no run of the agent saw the answer and the card asked for a wake. Never on a review Paperclip escalated to you. Once per card. [docs/watchdog.md](docs/watchdog.md#12-answers-that-reach-nobody)
- **Watchdog: reviews escalated by Paperclip's review-round limit can go back to the implementer.** After three agent change requests in a row on one review stage (`maxReviewRounds`), Paperclip hands the review to the responsible person instead of back to the implementer. That is deliberate, so it stays with you by default; with `WATCHDOG_RETURN_ESCALATED_REVIEWS=true` the watchdog returns it to the implementer with the reviewer's latest request, `WATCHDOG_MAX_NUDGES` times per issue (each return, as your decision, gives the agents `maxReviewRounds` more rounds). Raising `maxReviewRounds` in your execution policies is the other way. [docs/watchdog.md](docs/watchdog.md#13-reviews-escalated-by-paperclips-review-round-limit)
- **Watchdog: issues blocked by a cancelled issue.** Paperclip never counts a cancelled blocker as resolved, so its dependents stay blocked and nothing wakes their agents. With `WATCHDOG_CANCELLED_BLOCKERS` (default `true`) the watchdog tells the dependent's agent once, quoting the blocker's last comment, so it can remove or replace the blocker. [docs/watchdog.md](docs/watchdog.md#14-issues-blocked-by-a-cancelled-issue)
- **Relay: a PR's link goes on its own issue.** A newly opened PR's URL was posted on whichever issue waited on you among those the PR names, their subtasks and their blockers, so a PR could show up as another issue's (one PR was linked on the issue blocking its own). It now goes on the first issue the PR names, or that issue's subtask waiting on you. Your merge decisions still look further.
- **Watchdog: a dry run no longer uses up nudges.** With `DRY_RUN=true` the watchdog recorded each nudge it would have sent, so once dry run was off those situations counted as handled. It now logs each once and records nothing.
- **`pch status`** counts finished CI runs reported, flaky runs re-run and issues returned to their agent. The installers ask about the new settings.

## 1.7.0

- **Watchdog: question cards a teammate never sees are routed to it.** An agent asks a teammate with a question card addressed to it (`addresseeAgentId`) and waits in review. Paperclip wakes the teammate, then cancels that run before it starts ("Cancelled because issue assignee changed…"), because the teammate isn't the issue's assignee. The card waited for good, every issue blocked behind the asker waited with it, and none of it showed in **Decisions**. With `WATCHDOG_ROUTE_QUESTIONS` (default `true`), once such a card has waited for the stall window and the teammate has had no run on the issue since, the watchdog creates an issue assigned to the teammate, in the same project and priority, that quotes the question and says which card to answer and how. Answering the card wakes the asker. The watchdog closes that issue once the card is answered, withdrawn or expired. Once per card; a paused teammate waits until it's back; a card for a person or for anyone is left alone. The installers ask about it. [docs/watchdog.md](docs/watchdog.md#10-question-cards-addressed-to-a-teammate)
- **`pch blocked`: what the blocked issues wait on.** For every company: why each blocked issue is blocked (other open issues, every blocker done, a failed workspace clean-up, parked by recovery, held, or the agent's own note), which issues the chains of blocked issues end at, how many blocked issues each holds and what it waits on (a question card and who it's for, your approval, a reviewer, a run), and every question card that is waiting, with whether the watchdog has routed it. [docs/commands.md](docs/commands.md#blocked-what-the-blocked-issues-wait-on)
- **Watchdog: no hand-off nudge for a run that never started.** A run Paperclip cancelled as stale before it started (`issue_assignee_changed`, no `startedAt`), such as a teammate's wake for a question card, no longer counts as the issue changing hands. Before, the asker was nudged as the "new owner" while it waited on its card.
- **`pch why`** lists the issue's pending question cards and who each waits on. When the issue waits on a card Paperclip never delivered, that's the recommendation: answer it yourself, or give the teammate an issue to answer it (which the watchdog does by itself), or, once routed, the issue the watchdog created. A card for you is yours to answer. For an issue waiting on other open issues it also points at `pch blocked`.
- **`pch status`** counts the question cards the watchdog routed.

## 1.6.1

- **Watchdog: links to a closed workspace are cleared.** With `WATCHDOG_CLEAR_DEAD_LINKS` (default `true`), the watchdog finds open issues linked to an archived or missing workspace and clears the link, as `pch workspace --apply` does, so the next run gets a new isolated workspace. When the assignee's last run failed on that link and the issue is todo or in progress, it also comments to restart the agent. Blocked and in-review issues only have their link cleared. It keeps the issue's other workspace settings (a pinned branch, the environment), acts once per issue and workspace, and waits while a run is in progress or a workspace change is already scheduled. A refused change is tried again a stall window later, up to `WATCHDOG_MAX_NUDGES` times. It never touches a link to a live workspace, and leaves an issue linked to its own closed workspace to you. While Instance settings → Experimental → Enable Isolated Workspaces is off, Paperclip ignores the change, so the watchdog changes nothing and logs once a day which issues are affected. The installers ask about it. [docs/watchdog.md](docs/watchdog.md#8-issues-linked-to-a-closed-workspace)
- **Watchdog: an agent that scheduled a workspace of its own is woken.** An agent can't change its workspace during a run, but it can schedule one for its next run (`PUT /api/issues/:id/workspace`) and leave the issue in `todo`. Nothing started that run. Once such an issue has been quiet for the stall window with no run, the watchdog comments to wake the agent. Part of `WATCHDOG_CLEAR_DEAD_LINKS`.
- **`pch workspace --apply` keeps the issue's other workspace settings.** Paperclip replaces an issue's workspace settings whole on every update, so 1.6.0 dropped a pinned branch, the chosen environment, network egress and runtime settings along with the link. They are now sent back unchanged with the new mode.
- **`pch workspace` and `pch why`: a workspace your key can't read is no longer taken as closed.** Paperclip answers "not found" both for a missing workspace and for one the key may not read (issue privacy). The link is now judged from the issue's own copy of its workspace, which is what Paperclip checks when it starts a run.
- **`pch workspace` leaves alone an issue with a workspace change already scheduled for its next run** (clearing the link would cancel it), and one a run still holds.
- **`pch why`** says when the watchdog will clear a dead link by itself, and that it can't while Enable Isolated Workspaces is off.

## 1.6.0

- **`pch workspace ISSUE [--apply]`: issues linked to the wrong workspace.** An issue an agent creates from another issue's work is linked to that issue's execution workspace, and Paperclip has no setting to stop it. When that workspace is closed (Paperclip closes it when its issue finishes), every run on the linked issues fails at setup (`setup_failed`, "requested inherited execution workspace reuse … could not be restored"), and Retry and comments fail the same way. When it's another open issue's workspace, the linked issue's commits land on that issue's branch, and agents block and ask for a "workspace ruling". The command shows the link, and `--apply` gives the issue a new isolated workspace on its next run, as "New isolated workspace" in the Workspace picker does. With a closed workspace it fixes every open issue linked to it. It previews unless you pass `--apply`, skips issues with a run in progress, and checks that Paperclip took the change. If Instance settings → Experimental → Enable Isolated Workspaces is off, Paperclip drops the change without an error, and the command says so. [docs/commands.md](docs/commands.md#workspace-an-issue-linked-to-the-wrong-workspace)
- **`pch why`:** prints a `Workspace:` line for an issue linked to another workspace. It recommends `pch workspace` when that workspace is closed or the assignee's last run failed restoring it, instead of "open the run for the error" and a retry comment that fail again. For an issue an agent blocked over another issue's live workspace, it gives the command and the ruling to post.

## 1.5.1

- **Relay: a `/changes` or `/approve` that isn't recorded says so on the PR.** When the PR's issue isn't waiting on you, several are, it is already done, or the PR names no issue, the relay used to copy your text to an issue (or drop it) without a word on GitHub, so the command looked as if it never arrived, and the copy could land on a different issue from the one you meant. It now replies on the PR: which issues the PR names, which one got your text and its status and stage, why no decision was recorded, and the `pch` command to record it. The same goes for a "Request changes" review. A recorded decision gets no reply. Needs `GITHUB_TOKEN` or `GITHUB_TOKEN_FILE` with "Pull requests: Read and write"; it no longer needs `RELAY_FIX_CONFLICTS` for that. `RELAY_PR_NOTES=false` turns it off.
- **Compatibility suite:** Paperclip 2026.1012.0 passes, and is added to the releases the daily compatibility run checks.

## 1.5.0

- **Watchdog: no nudge loop when the model provider is out of capacity.** An issue Paperclip's recovery parked is no longer nudged for 6 hours after its last run failed on the provider (`provider_quota`, or a `*_transient_upstream` error, which is how Paperclip 2026.1005.0 files Claude's "You've hit your org's monthly spend limit"). Paperclip's own retries are spent by then, and a nudge only starts the same failing run. The watchdog logs it once and leaves it to you; after 6 hours (once a limit has usually reset, or you have resumed the agent) it nudges as before, within its budget. Before, each nudge led to two more failed runs and a new recovery action, and the nudge budget counted per action, so it never ran out: 333 runs on one issue in 17 hours.
- **Watchdog: the nudge budget for a parked issue is per issue and assignee,** not per recovery action. It starts again after a day. Counts kept under the old key are forgotten once on upgrade.

## 1.4.0

- **Relay: a GitHub App's token works, as well as a personal one.** `GITHUB_TOKEN_FILE` names a file holding the token, which the relay reads again for every GitHub request. A GitHub App installation token lasts an hour; whatever renews it on the host (for example paperclip-github-app's timer) writes the file, and the relay uses each new token at once, without a restart. `GITHUB_TOKEN` is unchanged for a personal access token, a person's or a machine account's. Set one of the two: the helper won't start with both. [docs/relay.md](docs/relay.md#a-token-file-github-app)
- **Installers:** for the conflict send-back they ask where the token comes from: pasted, or a file another program keeps fresh. They mount the file's folder read-only (a renewed file replaces the old one by rename, which a single-file mount wouldn't show), and warn when the helper's user may not be able to read it. A GitHub App token at `~/.cache/paperclip-github-app/token` is found and offered as the default, including in unattended installs.
- **Messages:** errors and `pch check` name the token's source. When GitHub rejects a token from a file, the log says how many minutes ago the file was last written, which shows at once whether its renewer stopped. A missing or empty file is reported as such.

## 1.3.0

- **Watchdog: holds Paperclip can never release by itself are released.** A run cut off at a hand-off, or one whose adapter failed before a process started, records no process id or stop. Paperclip then holds the issue for reconciliation ("Automatic recovery of this task stopped") and saves every message behind "The previous run has no verified stop record", for good. With `WATCHDOG_RELEASE_HOLDS` (default `true`), once the run has been over for the stall window, the watchdog records the board's reconciliation (the run stopped; what it did is unverified) and delivers the saved messages, or comments if there are none. Once per held run; a hold whose run is still active, holds a lease or recorded a process is only logged. The installers ask about it.
- **`pch release ISSUE [--apply]`:** releases an execution hold (`legacy_execution_requires_reconciliation`) whose run recorded no process or stop, e.g. one cut off at a hand-off. Paperclip can never prove such a run stopped, so messages and Interrupt were saved behind it indefinitely. The command records the board's reconciliation (run stopped, outcome unverified by default) and delivers the saved messages. It previews unless you pass `--apply`.
- **Compatibility suite:** Paperclip 2026.916.1, 2026.1001.0 and 2026.1005.0 pass. It reproduces a hold Paperclip can't release by itself (an agent whose command doesn't exist) and checks that the watchdog releases it and the saved message then starts the owner. Its test agents now run Node instead of `sh`, so the suite also runs on Windows, and it no longer waits out 2026.1005.0's minute-later retry of runs that leave no disposition.
- **`pch why`:** recommends `pch release` for that hold, instead of a message and Interrupt, which can't release it.
- **`pch status`:** shows Paperclip's version and build commit on the "Paperclip:" line, e.g. `(2026.1001.0, commit 8f8a0ab)`. Paperclip reports them only to an authenticated caller, so the helper asks with its key.

## 1.2.0

- **Relay: PRs with merge conflicts go back to their agents by themselves.** With many small PRs, each merge can leave other open PRs conflicting with the base branch, and they then wait for a review you can't finish. With `RELAY_FIX_CONFLICTS=true` and a `GITHUB_TOKEN`, the relay looks at the other open PRs after every merge (and every 15 minutes, in case a webhook was missed). For each one GitHub says conflicts, it requests changes on the PR's issue when its review is waiting on you, or comments on it otherwise, with a brief to bring the branch up to date, resolve the conflicts and push. It says so in a comment on the PR, so you can see it was already sent back.
  - A PR is sent back once per push, and after `RELAY_CONFLICT_MAX_ATTEMPTS` (2) pushes that still conflict it is left to you, with a note on the PR. Drafts, PRs that name no Paperclip issue, and PRs whose issue is done or cancelled are skipped.
  - Off by default. The installer asks about it and for the token; [docs/relay.md](docs/relay.md#the-github-token) has the steps to create one. `pch check` tests that the token can read your repositories, and `pch status` counts the PRs sent back.
  - The helper still never merges, pushes, closes or deletes anything. The token is used to read pull requests and to comment on them.
- **Logs:** GitHub tokens are masked, like Paperclip keys.

- **`pch why`:** ends with a recommendation: what is holding the issue, the steps or commands that get it moving, and whether the watchdog does it by itself. It also shows the latest comment, an issue Paperclip's recovery parked, and saved messages that are waiting. `pch why ISSUE --prompt` prints all of it, with the last three comments, as a prompt for an LLM chat.
- **Watchdog:** an issue Paperclip's recovery parked because it couldn't run the assignee (`stranded_assigned_issue`: "Automatic recovery blocked … the original assignee is not invokable", typically after agents were paused) is un-parked once the agent is available: the watchdog delivers its saved messages, or comments on it. Any other kind of recovery action is reported once and left to you. Paperclip reports these as recovery actions, not as an execution hold, so the 1.1.0 release of holds never saw them.

## 1.0.0

First public release, as a published image with installers for Linux, macOS and Windows.

- **Relay:**
  - Merging a PR approves the Paperclip issue waiting on you. Request changes and `/changes` send it back, and your other comments are copied.
  - A merge that names a parent issue approves the subtask waiting on you. If several wait and none lists the PR, it comments instead of guessing.
  - A newly opened PR's URL is posted on its issue, so Paperclip links it (`RELAY_LINK_PRS`).

  - Dropped hand-offs, blocked issues whose blockers are done, and blockers stuck on a failed workspace clean-up.

  - A wake deferred behind a stuck run is reported once. `WATCHDOG_RETRY_DEFERRED` asks Paperclip to retry it through its "send queued messages now" action. Only the assignee's own wakes count, so a wake deferred for the previous owner, or one that later runs have overtaken, doesn't hide a dropped hand-off.

  - Runs by agents that were since terminated are still synced.
  - Fractions of a cent are carried per agent and model instead of being rounded away.
  - The preview shows budget impact.
  - Idempotent across crashes, with a guard against a lost or unreadable state file.
- **Commands:** `status`, `check`, `why`, `approve`, `changes`, `comment`, `costs` (and `costs --sessions`), `models`, `set-model`, `login`, `revoke`, `secret` and `version`.
