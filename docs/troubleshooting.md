# Troubleshooting

Start with `pch status` and, for a stuck issue, `pch why ISSUE`.

| Symptom | Cause and fix |
|---|---|
| `Paperclip refused the hostname …` | [The hostname guard](install.md#paperclips-hostname-guard-http-403): allow the hostname, or use host networking. |
| `cannot reach Paperclip at http://127.0.0.1:3100` | From a container, `127.0.0.1` is the host only with `network_mode: host`. Check `PAPERCLIP_API`, or re-run the installer. |
| `Paperclip rejected the helper's board key` | It expired or was revoked. Run `pch login`. |
| `pch status`: `Watchdog: on. Last check … (190.7 s)`, and the watchdog acts minutes late | The lines under it name the slowest parts of the check and the slowest kinds of request. A slow `GET /api/issues/:id/runs` or `GET /api/issues/:id` is Paperclip building that answer (a long run history or activity log); a slow listing is a large board. See [how long a check takes](watchdog.md#how-long-a-check-takes). |
| `config: …` lines, and the container restarts | A setting is missing or invalid. The line names it. |
| `another Paperclip Helper is already running on this data directory` | A second copy of the service (`pch run`, or a bare `pch` from an older `pch` script) found the first one's heartbeat in `data/status.json`, and stopped before doing anything, so agents aren't nudged and costs aren't posted twice. Nothing to fix: `pch status` shows the one that is running. A start right after a crash can wait up to 40 seconds while it checks that the old one's heartbeat has stopped. |
| `relay could not listen on 127.0.0.1:3110: something already listens there` | Another program has the relay's port, or a helper with another data directory does. `pch status` shows whether this helper is running. Stop the other program, or set `RELAY_PORT` to a free port and point the webhook (or tunnel) at it. |
| Deliveries show 401 in GitHub | The webhook secret doesn't match `GITHUB_WEBHOOK_SECRET`. |
| A delivery shows **202** with `still working after 8s` | The relay was still looking for the PR's issues when GitHub's 10 seconds were nearly up, so it answered and carried on. The log's `relay: handled` (or `relay: failed`) line for that delivery id says what it did. A failed one can be redelivered. |
| A delivery failed with `Task is paused` | Paperclip refuses comments on a paused task. Resume it, then **Redeliver** in GitHub. |
| Deliveries show `names no ACM issue` | The PR's title, branch and body contain no issue identifier. |
| A **`/changes` or `/approve` did nothing** you can see | It reached the relay, but the PR's issue wasn't waiting on you, so your text was copied to the first issue the PR names as a comment. With a GitHub token the relay replies on the PR saying which issue and why. Record the decision with `pch changes ISSUE "…"`. |
| A merge only comments (`decision is not waiting on you`) | The approval stage isn't pending on your user. `pch check ISSUE` shows who it's waiting on. |
| A merge leaves the issue **in review**, "Approval pending with You" | The merge approved an earlier stage of yours and the next one belongs to someone else, or the relay is older than 1.0.1. The delivery's response has a `warning` naming who it's waiting on. |
| A PR has **merge conflicts** after you merged another | Turn on [`RELAY_FIX_CONFLICTS`](relay.md#prs-with-merge-conflicts) and the relay sends it back for you. Without it, comment `/changes Merge main and resolve the conflicts` on the PR. |
| `relay: conflict check failed` with **`GET …/pulls/N → 404: Not Found`** although the token or App has Pull requests access | GitHub answers 404 both for what isn't there and for what a token can't see. If the message says the same token listed the PR moments before, it isn't a permission: the sweep asked again five times, and checks the PR on the next sweep. Otherwise run `pch check`: it lists each repository's PRs and reads one on its own, and says which of the two fails. A list that fails too means the token can't see the repository (the App's repository selection, or the repositories the token is limited to). `pch check` runs in the helper's container, so `GITHUB_TOKEN_FILE` is the path inside it, not on the host. |
| A conflicting PR **wasn't sent back** | Look for `relay: conflict sweep` in the log: each PR it left alone has a `reason` (a draft, names no issue, already sent back and waiting for a push, attempts used up, no single issue owns it). `pch check` tests the token. GitHub can take a minute to notice a conflict; the next look picks it up. |
| A conflict notice **landed on the wrong issue** (before 1.15.1), or the board was told **no single Paperclip issue owns** a PR | Since 1.15.1 a conflict or failed-check send-back goes only to the issue that lists the PR as a work product, else the one its title starts with, else the one whose workspace branch is its head branch ([relay](relay.md#prs-with-merge-conflicts)). When those disagree or none matches, nothing is sent to any issue. Record the PR as a `pull_request` work product on its issue, or start the PR's title with the issue's identifier, and push; or send it back yourself with `pch changes <issue> "…"`. |
| The log says **could not comment on the PR** | The token can read but not write. Give it "Pull requests: Read and write", or set `RELAY_CONFLICT_PR_COMMENT=false`. The PR was still sent back. |
| Every run fails at once with **`setup_failed`: "requested inherited execution workspace reuse … could not be restored"** | The issue is linked to a closed workspace, usually that of the issue it was created from. Run `pch workspace ISSUE --apply`, then comment to restart the assignee. See [`workspace`](commands.md#workspace-an-issue-linked-to-the-wrong-workspace). |
| Every run fails within seconds with **`workspace_validation_failed`**: "The selected execution workspace's original repository could not be verified", and the issue is blocked with a board recovery action | Paperclip couldn't verify the issue's git worktree. `pch why ISSUE` names the reason code. With `source_registration_unproven`, the usual cause is git's `worktree.useRelativePaths` (git 2.48 or newer) for the user Paperclip runs as: git writes the worktree's links as relative paths, which Paperclip can't follow, so every worktree made since fails, though git sees nothing wrong. `cat <worktree>/.git`: a `gitdir:` that doesn't start with `/` confirms it. Run `pch worktrees --links` and the repair it prints on Paperclip's host (the repository's own `worktree.useRelativePaths false`, then `git worktree repair --no-relative-paths` over every worktree), then `pch worktrees --links --retry`. See [`worktrees --links`](commands.md#worktrees---links-every-run-fails-at-setup-on-relative-worktree-links). |
| Every `dotnet build` in every worktree fails with **`Unsupported repository extension 'relativeworktrees'`** (or a libgit2-based tool refuses the repository), usually right after a relative-worktree repair | The checkout's config still has `extensions.relativeWorktrees`, which git turned on when it wrote relative worktree links and which `git worktree repair --no-relative-paths` leaves behind. Git and Paperclip don't mind it; tools with their own git reader (.NET SourceLink's `Microsoft.Build.Tasks.Git`, libgit2) refuse it. `git -C <checkout> config --get extensions.relativeWorktrees` prints `true`. Once no worktree link is relative (both counts in the repair print 0), on the host: `git -C <checkout> config --unset extensions.relativeWorktrees`. The repair from 1.14.1 on ends with this, guarded by the counts; `pch why ISSUE` prints it when an agent reports the error. |
| An agent blocks an issue asking for a **"workspace ruling"**, or says it would commit on another issue's branch | The issue is linked to another issue's live workspace. If it should have its own branch and PR, run `pch workspace ISSUE --apply` and say so in a comment. |
| `pch workspace` says **Paperclip ignores workspace changes** | Turn on Instance settings → Experimental → Enable Isolated Workspaces. |
| An issue is **blocked with nothing in "Blocked by"** | Either an agent blocked it with a note of its own, or Paperclip's recovery did. `pch why ISSUE` shows an execution hold if there is one; see [what the watchdog leaves to you](watchdog.md#what-it-leaves-to-you). |
| An agent **runs every few minutes** and posts the same "Blocked: …" note | It's waiting on something only you can do, usually an approval. Decide it, or pause the issue. |
| "**The original assignee is not invokable**" | The agent, or one above it in the org chart, was paused, terminated or awaiting approval when Paperclip's recovery ran. Resume it. If the agent itself was paused, the watchdog restores its issues blocked during the pause ([15](watchdog.md#15-issues-blocked-while-their-agent-was-paused)); others it un-parks with a comment; `pch why ISSUE` gives the command to do it yourself. |
| **Agents still paused after the watchdog resumed them** (`agent.resumed` in the activity log, `pauseReason` empty) | Paperclip never finished pausing them: an old run or workspace lease of theirs isn't cleaned up, and a resume takes effect only after the pause is done. `pch models` shows `no hold, still pausing`. Resuming again won't help; restart Paperclip, and clean up a lease whose clean-up failed. The watchdog tells the board after ten minutes and again when they are back ([16](watchdog.md#a-resume-that-doesnt-take-effect)). |
| **Agents paused by themselves** | A usage limit (Claude or Codex): the watchdog paused the agents on that account ([16](watchdog.md#16-usage-limits)). The log (and `WATCHDOG_NOTIFY_ISSUE`) says until when; they are resumed a few minutes after the reset. Resume one yourself whenever you like; `WATCHDOG_USAGE_LIMIT_PAUSE=false` turns it off. A Codex agent resumed an hour early or late: `WATCHDOG_LIMIT_TIME_ZONE` isn't your time zone (the installer sets it from the machine it runs on); correct it in `.env`. |
| An issue the agent closed **was reopened by the watchdog** | It closed while its own PR was still open, after an agent's update wiped its review stages ([17](watchdog.md#17-issues-whose-review-stages-were-wiped)). Restore its review stages; the watchdog doesn't re-create them. |
| A PR **dropped from the merge queue** wasn't sent back | The queue removed it for a cancelled run or its status-check timeout, not a failed check, so the relay told the board instead ([relay](relay.md#prs-the-merge-queue-drops-without-a-conflict)). Queue it again. The log line `relay: merge-queue drop` says what it found. |
| **"Recovery needed. Execution was cancelled; its source was not recorded. Automatic recovery stopped… Inspect the run before sending a new message to request continuation. N saved message(s) waiting for recovery."**, only **Inspect run** to press, and comments or status changes start no run | Paperclip cancelled a run before it started (`issue_assignee_changed`, `issue_disposition_repair_superseded`, …) and still holds the issue for reconciliation behind it, for good. `pch why ISSUE` says "Held run never started". From 1.16.0 the watchdog releases it as not performed and delivers the saved messages ([22](watchdog.md#22-holds-behind-runs-that-never-started)); `pch release ISSUE --apply` does it by hand. On a held review (the run is its reviewer's), from 1.16.1 it keeps the review if Paperclip has parked it in `blocked`, or, still in review at an untouched first stage, starts that stage again with the same reviewer and implementer. On any other pending review it won't: a Paperclip with paperclipai/paperclip#18838 releases it by itself. From 1.16.1, when the issue belongs to another agent (you gave it on, or the held reviewer's review ended), it asks the held run's agent to hand it on. An issue waiting on CI that is held again every few minutes, behind `issue_disposition_repair_superseded` or `legacy_disposition_repair_suppressed` runs ("Disposition repair suppressed: durable_wait"), with `issue_recovery_action_restored` wakes between: the Helper's CI backstop and its release chasing each other. From 1.17.0 the watchdog keeps such a hold until the CI run finishes and then releases it with the run's report, so the agent wakes once (see the next row). Don't reassign a held issue yourself while a run is queued or starting on it: that cancels the run and Paperclip holds the issue behind it too. If `pch why` doesn't say the run never started, the run did execute: inspect it before you release it. |
| `couldn't release a hold Paperclip can't release by itself; left to you`, with `queued-comments/interrupt → 409: The queued message is no longer pending` | Logged by 1.15.3 and earlier. The release itself worked (the request that failed came after it): once the hold was gone Paperclip started the saved messages itself, before the helper pressed Interrupt. `pch why ISSUE` should show no hold and the agent's run. From 1.16.0 that is counted as released. |
| `couldn't release a hold …`, with `recovery-actions/resolve → 409: Safe recovery hand-back cannot bypass a pending execution review or approval stage` | The issue's review stage is pending, and Paperclip releases a hold only by moving the issue to `todo`, which it refuses while the review is pending. Nothing changed. From 1.16.1 the watchdog releases a held review by a route that keeps it, or starts its untouched first stage again ([22](watchdog.md#22-holds-behind-runs-that-never-started)). |
| `couldn't release a hold …`, with `recovery-actions/resolve → 409: The recovery source or task owner changed` | The held run is another agent's than the assignee's: Paperclip accepts the release only while the run's agent has the issue. From 1.16.1 the watchdog gives the issue back to that agent a moment and asks it to reassign the issue on itself ([22](watchdog.md#22-holds-behind-runs-that-never-started)); `pch release ISSUE --apply` does the same. A board reassignment back while that agent's run is queued or starting would hold the issue again ([why](paperclip-internals.md#how-a-board-reassignment-makes-new-holds)). |
| An agent **waiting on CI sits for hours after the run finished**, until the Helper's backstop fires (`issue.monitor_triggered`, six hours after the wait began by default), with no "the CI run you were waiting on has finished" comment | Up to 1.17.0, the report was skipped when the agent's latest comment came after the run finished, even one that said it was still waiting on that run (a recovery run's "… is waiting on run …"), or when the issue's `executionRunId` or `checkoutRunId` still named a run that never started, which skipped the issue without a word. From 1.17.1 such comments don't count as having seen the run, those fields don't skip the issue, and whenever a finished run isn't reported for any other reason than the agent having seen it, the backstop is brought forward to a stall window from now ([11](watchdog.md#11-ci-runs-an-agent-waits-on)). With `LOG_LEVEL=debug`, search the log for the run id: "a finished CI run an agent waits on isn't reported" gives the `reason`, and "brought the CI backstop forward" says when it will fire. |
| An agent **waiting on CI is woken every few minutes for nothing**: runs that only post "still waiting on CI", the issue held (`legacy_execution_requires_reconciliation`), released (`handed_back`, "the held run stopped without a record Paperclip could verify" or "… was cancelled before it started"), blocked again, and "every blocker on this issue is done … Please continue it" nudges on an issue whose old blockers happen to be done | Three watchdog actions fed each other up to 1.16.3: the release of a hold on an agent waiting on CI woke it; the blockers-resolved nudge reopened the held issue (clearing the backstop) and woke it; and the run ending without the backstop was the next repair and the next hold. From 1.17.0 the hold is kept until the CI run finishes and released with its report ([how](watchdog.md#holds-on-an-agent-waiting-on-ci)), the nudge leaves a held issue alone ([2](watchdog.md#2-blocked-issues-whose-blockers-are-all-done)), and the [loop breaker](watchdog.md#the-loop-breaker) stops any watchdog wake that repeats twice in half an hour with nothing moving on the issue, telling the board once. The log names each decision: "a hold on an issue waiting on CI is kept until the run finishes", "no blockers-resolved nudge: the issue is held for recovery, not by its blockers", "a wake held back by the loop breaker". |
| **"Recovery needed"** on an issue waiting for CI: a system comment "Paperclip exhausted the bounded original-owner disposition repair without a durable source-state change … Terminal reason: `unchanged_source_state_exhausted` … Recovery owner: board", after `issue_disposition_repair` runs that each found the CI still queued | The agent named the run and ended its run, leaving the issue in progress with no run and no monitor, which Paperclip's disposition guard counts as no live path: it wakes the agent twice to repair that, then blocks the issue for the board ([the guard](paperclip-internals.md#the-disposition-guard-an-issue-in-progress-needs-a-live-path)). From 1.15.0 the watchdog gives such an issue a backstop monitor while the run is going ([11](watchdog.md#11-ci-runs-an-agent-waits-on)), which Paperclip counts as the live path: at most the first repair run happens, and no escalation. Check `WATCHDOG_CI_RUNS` is on, the GitHub token can read the run, the run's repository is in `GITHUB_REPOS`, and `WATCHDOG_CI_BACKSTOP_MIN` isn't 0; `pch why ISSUE` says whether the backstop stands. For an issue already escalated: the run's result is still reported when it finishes, and moving the issue back to in progress (or a board comment) hands it back to the agent. |
| An agent **wakes every few seconds** with "still waiting" (or the same short note), dozens of runs an hour on one issue | Its runs end without a comment of its own, Paperclip posts each run's final message as the agent's comment (`run_presentation_resolver`), and that comment wakes the same agent again. Pause the issue (or the agent) to stop it, and tell the agent to end every run with a comment of its own ([the wording](watchdog.md#what-to-tell-agents-about-ci)). The watchdog tells the board once per issue ([21](watchdog.md#21-agents-that-wake-themselves)) and never comments on the issue, which would wake it again. `pch why ISSUE` names it. |
| An agent's **monitor was replaced** by a "Paperclip Helper CI backstop" monitor | Its monitor polled a CI run (next check within half the backstop). The backstop checks once, hours out, and is cleared when the watchdog reports the run ([11](watchdog.md#11-ci-runs-an-agent-waits-on)). Tell the agent not to set monitors for CI runs. |
| An agent's **monitor disappeared** after a CI report | Its notes named only the run the watchdog reported, so it was cleared in the same step ([11](watchdog.md#11-ci-runs-an-agent-waits-on)): it would only have woken the agent to find the run finished. |
| Where did the **"PR #12 opened by …" comments** go? | Into the issue's **Pull requests** document, which wakes nobody (`RELAY_QUIET_NOTES`). |
| **Answering a card through the API is refused** ("requires an answer") | Send a typed answer as `otherText`, not `text`, or use `pch answer ISSUE CARD "…"`. |
| No PR rows on the issue | Turn on **Instance settings → Experimental → External Objects**. |
| Synced costs under *Unattributed* on the Costs page's *By project* | Events posted by 1.15.2 and earlier carry no project, and Paperclip's API can't add one afterwards; from 1.15.3 each event carries its run's project. A run with no issue and no project (a timer run) is still unattributed. `pch costs` shows where the runs not yet synced will land. See [cost sync](cost-sync.md#which-project-a-cost-lands-under). |
| Codex costs missing | Look for `pch costs` lines such as `model unknown` or `no price for …`, then set `CODEX_DEFAULT_MODEL` or add the model to `prices.json`. |
| `cost sync: Paperclip rejected a cost event` | The warning before it, `Paperclip's answer to a rejected cost event`, has Paperclip's whole answer (for a `400: Validation error`, each field it refused and why) and the fields the post had. Once the cause is fixed, `pch costs --retry-skipped` posts those runs again. See [cost sync](cost-sync.md#when-paperclip-rejects-a-cost-event). |
| Anything else | `docker compose logs --tail 50`. There's one JSON line per event; `LOG_LEVEL=debug` shows more. |
